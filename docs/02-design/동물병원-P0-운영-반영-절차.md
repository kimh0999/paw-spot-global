# 동물병원 P0 운영 반영 절차

이 문서는 각 단계에 무엇을 확인하고 어떻게 되돌리는지 적는다.

> **진행 상태 (2026-09-13 기준)**
>
> | 단계 | 상태 |
> |---|---|
> | 3-1 마이그레이션 | **완료** — §7 실행 기록 참조 |
> | 3-2 앱 배포 | 미실행 |
> | 3-3 데이터 검수 | 미실행 (병원 0곳) |
> | 3-4 공개 | 미실행 |

전제: 이 저장소의 운영 DB는 Supabase **한 벌**뿐이다. 되돌릴 스테이징이 없으므로
"되돌릴 수 있는가"를 단계마다 먼저 묻는다.

## 1. 반영 대상

| 종류 | 내용 | 되돌릴 수 있나 |
|---|---|---|
| 마이그레이션 | `20260910000000_vet_clinic` — enum 2개, 테이블 2개, 인덱스 3개, FK 1개 | 예. 전부 신규 객체라 DROP으로 되돌아간다 |
| 앱 | 병원 목록·상세·관리자 화면, 헤더의 `동물병원` 링크 | 예. 이전 버전 배포로 되돌아간다 |
| 데이터 | 병원 행 등록 | 예. 행 삭제 또는 `visibility` 되돌리기 |
| 공개 | `visibility = VISIBLE` 전환 | 예. `HIDDEN`으로 되돌리면 목록·상세·직접 URL 모두에서 사라진다 |

마이그레이션은 **추가만 한다.** 기존 테이블·컬럼·enum 값을 바꾸거나 지우지 않으므로
구버전 앱이 돌고 있어도 깨지지 않는다. 이것이 아래 순서를 가능하게 하는 전제다.

## 2. 사전 확인

1. **적용 대상이 운영인지 눈으로 확인한다.** `prisma.config.ts`는
   `MIGRATE_DATABASE_URL ?? DIRECT_URL`을 쓰고, dotenv는 이미 설정된 환경변수를
   덮어쓰지 않는다. 즉 셸에서 넘긴 값이 이긴다. 적용 전에 호스트와 DB 이름을
   출력해 확인한다. **연결 문자열 전체나 비밀번호를 출력하지 않는다.**
2. **미적용 마이그레이션 목록을 먼저 본다.** `prisma migrate status`.
   `20260910000000_vet_clinic` 외에 다른 것이 딸려 들어가지 않는지 확인한다.
3. **PostGIS가 이미 설치돼 있는지 확인한다.**
   `SELECT extversion FROM pg_extension WHERE extname = 'postgis';`
   이 저장소의 마이그레이션 이력에는 `CREATE EXTENSION postgis`가 **없다.**
   Supabase가 확장을 제공하기 때문이며, 확장이 없는 PostgreSQL에서는
   `geography` 컬럼 생성이 실패한다.
4. **백업 시점을 확인한다.** 되돌릴 필요는 신규 객체 DROP으로 충분하지만,
   되돌릴 수 없는 상황(오적용 대상)에 대비해 마지막 백업 시각을 적어 둔다.

## 3. 적용 순서

**마이그레이션 → 앱 배포 → 데이터 검수 → 공개** 순이다. 이 순서인 이유는 각각 다르다.

### 3-1. 마이그레이션 먼저

앱을 먼저 배포하면 테이블이 없는 상태에서 `/vets`가 열려 조회가 실패한다.
반대로 마이그레이션이 먼저 들어가면 구버전 앱은 새 테이블을 아예 모르므로 아무 일도
일어나지 않는다.

```
npx prisma migrate deploy
```

`migrate deploy`를 쓴다. `db push`는 스키마 파일을 기준으로 DB를 맞추는 명령이라
이력에 남지 않고 의도치 않은 변경까지 끌고 갈 수 있다. shadow DB도 필요 없다.

적용 후 확인: `\d "VetClinic"`, `\d "VetVerification"` — 컬럼·기본값·인덱스와
`VetVerification_clinicId_fkey`의 `ON DELETE CASCADE`.

### 3-2. 앱 배포

이 시점에 헤더의 `동물병원` 링크와 `/[locale]/vets` 경로가 사용자에게 열린다.

**테이블이 없는 동안 새 경로가 노출되는 구간은 이 순서에서는 생기지 않는다.**
마이그레이션이 이미 끝났기 때문이다. 만약 부득이 앱을 먼저 배포해야 한다면,
링크를 감추는 것만으로는 부족하다 — 경로는 URL로 직접 열린다. 그때는 배포를
미루는 쪽이 맞다.

병원이 한 곳도 없는 상태로 열려도 화면은 `병원 0곳`을 보여준다. 이것은
**빈 목록**이지 오류 숨김이 아니다. 조회가 실패하면 0곳이 아니라 오류로
드러나야 하며, 공개 화면을 고정 데이터로 대체하지 않는다.

### 3-3. 데이터 검수 (공개 전)

병원은 `DRAFT`로 등록하고 관리자 화면에서 검수한다. 수집한 표본
(`scripts/vet-samples.daejeon.json`)은 전부 `DRAFT`이며 항목별로 `검토 필요`가
적혀 있다. 최소한 다음을 사람이 확인한 뒤에 공개로 넘긴다.

- **도로명 상세주소.** 표본의 출처는 소재지를 동 단위까지만 준다.
  D-20 공개 게이트는 주소 **문자열이 있는지만** 보므로 `대전광역시 서구 도안동`
  같은 값도 통과한다. 자동으로 막히지 않는다는 뜻이며, 이 검수가 유일한 방어선이다.
- **전화번호.** 출처 표기가 제각각이고 구분자가 없는 항목이 있다. 끊어읽기가
  추정인 번호는 공개하지 않는다.
- **진료시간·야간 진료·영어 응대.** 출처에 없으면 `UNKNOWN`으로 둔다.
  상호의 `24시`를 야간 진료의 근거로 삼지 않는다.
- **확인 방법.** 웹 조회는 `WEBSITE`다. 전화·DM으로 확인하지 않은 것을
  `PHONE`·`DM`으로 기록하지 않는다.

### 3-4. 공개

관리자 화면에서 `visibility`를 `VISIBLE`로 바꾼다. 서버가 `canPublishClinic()`으로
다시 판정하므로 폼을 우회해도 기준 미달은 저장되지 않는다(격리 DB 통합 테스트로
확인함 — 권한 없는 호출은 거절되고 행이 생기지 않는다).

한 곳씩 공개하고 화면에서 확인한 뒤 다음으로 넘어간다.

## 4. 적용 후 확인

| 확인할 것 | 기대 |
|---|---|
| `/ko/vets`, `/en/vets` | 200. `VISIBLE`만 목록에 나온다 |
| `DRAFT`·`HIDDEN` 병원의 상세 URL 직접 접근 | 병원 내용이 **전혀** 나오지 않는다 |
| 공개 응답 본문 | `adminNote`·`verifiedBy`가 없다 |
| `/ko/admin/vets` (비관리자) | 로그인으로 보내거나 `forbidden`. 목록이 보이지 않는다 |
| 좌표 없는 병원 | `위치 미등록`. 거리를 만들어 내지 않는다 |
| 확인 30일 경과 | `재확인 필요` 표시. 단 공개가 취소되지는 않는다(D-18) |
| 모바일 하단 고정 바 | 마지막 문단을 가리지 않는다 |

## 5. 되돌리기

되돌릴 범위를 **가장 작은 것부터** 고른다. 아래로 갈수록 영향이 크다.

1. **공개만 되돌린다.** 문제 병원을 `HIDDEN`으로. 즉시 목록·상세·직접 URL에서
   사라진다. 데이터는 남으므로 다시 검수해 공개할 수 있다. 대부분의 데이터
   문제는 여기서 끝난다.
2. **기능 노출을 되돌린다.** 이전 앱 버전으로 배포를 되돌린다. 테이블은 남지만
   구버전 앱은 참조하지 않으므로 해가 없다. 화면 결함일 때 쓴다.
3. **마이그레이션을 되돌린다.** 신규 객체만 지우면 된다. 앱을 먼저 되돌린 뒤에
   실행한다. 순서를 바꾸면 배포된 앱이 없는 테이블을 조회한다.

```sql
DROP TABLE IF EXISTS "VetVerification";
DROP TABLE IF EXISTS "VetClinic";
DROP TYPE IF EXISTS "VetVerificationTarget";
DROP TYPE IF EXISTS "VetServiceStatus";
DELETE FROM "_prisma_migrations" WHERE "migration_name" = '20260910000000_vet_clinic';
```

`VetVerification`을 먼저 지운다 — FK가 `VetClinic`을 참조한다. `PlaceVisibility`와
`VerificationMethod`는 **지우지 않는다.** 장소 도메인이 쓰고 있는 기존 enum이다.

`_prisma_migrations` 행을 지우지 않으면 다음 `migrate deploy`가 이미 적용된 것으로
보고 건너뛴다.

### 7-1. 사전 확인 결과 (§2)

| `_prisma_migrations` | **적용 직전 기준 8건**(= 9개 중 `vet_clinic`만 미적용) 전부 `finished` · `rolled_back_at` 없음 · **실패·부분 적용 0건** |
| 기존 vet 테이블 | 없음 (신규 생성이 맞음) |

### 7-2. 실행

```
npx prisma migrate deploy
```

`migrate dev`·`migrate reset`·`db push`는 쓰지 않았다. 마이그레이션 파일은 수정하지 않았고,
스키마 적용 없이 이력만 완료 처리하지도 않았다.

### 7-3. 적용 후 확인 (§3-1)

이력이 아니라 **실제 객체**를 조회해 확인했다.

| 대상 | 확인 결과 |
|---|---|
| 이력 | `20260910000000_vet_clinic` · `finished` · `applied_steps_count = 1` |
| `VetClinic` | 19컬럼. `location`은 `geography` **nullable**, `englishSupport`·`afterHours` 기본값 `'UNKNOWN'`, `visibility` 기본값 `'DRAFT'` |
| `VetVerification` | 10컬럼. `verifiedValue` 포함 |
| 인덱스 | `VetClinic_visibility_idx` · `VetClinic_district_idx` · `VetVerification_clinicId_target_idx` + PK 2개 |
| FK | `VetVerification_clinicId_fkey` — `ON UPDATE CASCADE ON DELETE CASCADE` |
| enum | `VetServiceStatus`(4값) · `VetVerificationTarget`(4값) |
| 기존 데이터 | `Place` **6행 그대로.** 기존 테이블·enum·데이터 변경 없음 |

**숫자 정리 — 8과 9는 같은 DB의 전후다.** 저장소에는 `migration.sql`을 가진
마이그레이션이 **9개**이고(`migration_lock.toml`은 파일이라 세지 않는다), 적용 직전 운영 DB에는
그중 8개가 들어 있었다. `vet_clinic` 하나를 적용해 **9개가 됐다.** 격리 DB(§8)는 빈 상태에서
시작하므로 같은 9개를 한 번에 적용한다. 이름별로 대조했을 때 저장소·운영 양쪽 모두 9개가
완전히 일치하며 **미적용은 0건**이다(2026-09-13 읽기 전용 확인, `migrate status`도
`Database schema is up to date!`).

### 7-4. 조회 동작 확인

Prisma Client를 재생성(`prisma generate`)한 뒤 실제 연결로 조회했다. `P2021`·
`VetClinic does not exist`는 **더 이상 발생하지 않는다.**

| 조회 | 결과 |
|---|---|
| 공개 목록 (`visibility: VISIBLE`) | 0행 — **정상 빈 상태** |
| 없는 ID 상세 | `null` → 상세 페이지는 `notFound()` |
| 관리자 목록 | 0행 |
| `verifications` 관계 조인 | 성공 |
| `VetVerification` 단독 조회 | 0행 |

병원이 0곳인 것은 **아직 등록하지 않았기 때문**이다. 조회 실패를 0건으로 숨긴 것이 아니며,
`/vets`는 실패 시 `loadFailed` 플래그로 빈 목록과 구분해 다른 안내를 낸다.

### 7-5. 이번에 하지 않은 것

- **데이터 등록.** 운영 DB는 한 벌뿐이라 검증용 병원·seed를 넣지 않았다. §3-3 검수는
  운영자가 실데이터로 수행할 단계다.
- ~~**저장·수정·삭제 통합 검증.**~~ **해소됨 (2026-09-13).** Docker를 기동해 격리 DB에서
  실행했다. §8 참조.
- **앱 배포·공개 전환.** §3-2 이후 단계는 운영자 판단으로 남는다.

| 정상 공개 병원 상세 조회 | 관리자 메모 제외 · 좌표 유무별 거리 | 통과 |
| **삭제 시 확인 기록 처리** | 병원을 지우면 확인 기록도 사라진다 (FK CASCADE) | 통과 (신규) |
| **없는 ID 처리** | 공개·관리자 조회 모두 null | 통과 (신규) |

**삭제는 제품에 경로가 없다.** 관리자 화면·서버 액션·`save-clinic` 어디에도 병원을 지우는
함수가 없다. 그래서 신규 테스트가 확인한 것은 **마이그레이션이 선언한 `ON DELETE CASCADE`가
실제로 그렇게 도는가**뿐이며, 제품에 삭제 기능을 만들어 넣지 않았다.

### 8-3. 역할별 권한

세 역할을 **실제 서버 처리 지점**에서 갈랐다. 권한 판정은 세션의 주장이 아니라
**DB의 `role`을 다시 읽으므로**, 테스트는 관리자·일반 사용자를 격리 DB에 실제로 만든다.

| 지점 | 비로그인 | 일반 회원 | 관리자 |
|---|---|---|---|
| 생성 액션 | 거절 · DB 불변 | 거절 · DB 불변 | 저장됨 |
| 수정·공개 전환 액션 | — | 값을 바꾸지 못함 | 반영됨 |
| 확인 기록 추가 | — | 추가하지 못함 | — |
| **조회 가드**(`requireAdminPage`) | `/ko/login`으로 | **`/ko/forbidden`으로** (로그인 화면이 아니다) | 통과 · role=ADMIN |
| 세션 이메일이 DB에 없을 때 | — | — | `/ko/forbidden` (관리자로 보지 않음) |

공개 기준(D-20)을 못 채우면 **관리자여도** 공개되지 않는 것도 함께 확인했다.

**이 검증의 층위.** `auth()` 세션만 대체(mock)했고 액션·권한 로직·DB 왕복은 전부 제품
코드다. 따라서 단순 mock 통과가 아니다. 다만 **실제 로그인 세션의 브라우저 조작은 여전히
확인하지 않았다** — 그 항목은 §6에 남는다.

## 9. 실행 기록 — 브라우저 관리자 흐름 (2026-09-13)

§8의 자동 테스트와 달리, **실제 화면을 조작해** 관리자 흐름을 확인했다.

### 9-1. 인증 범위 — 먼저 분명히 한다

이 저장소의 로그인 제공자는 **Google OAuth 하나뿐**이다(`src/auth.ts`). 계정 접근과
대화형 동의가 필요해 **로그인 과정 자체는 수행하지 않았다.**

대신 앱과 **같은 `AUTH_SECRET`·같은 `next-auth/jwt`**로 세션 쿠키를 발급해 브라우저에
넣고 로그인 이후 화면을 조작했다. **제품 코드는 수정하지 않았고 인증 우회 기능도 넣지
않았다.** 역할 판정은 서버가 DB의 `role`을 다시 읽으므로 이 쿠키로 관리자를 위조할 수
없다 — 격리 DB에 `ADMIN`·`USER` 사용자를 실제로 만들어 확인했다.

**따라서 이것은 로그인 E2E가 아니다.** 남는 미검증은 "Google 로그인 화면에서 시작하는
전체 흐름"이다.

### 9-2. 확인한 흐름 (격리 DB, 관리자 세션)

| 단계 | 화면 조작 | 결과 |
|---|---|---|
| 등록 | `/ko/admin/vets/new`에서 병원명·주소·전화 입력 후 `등록` | `DRAFT`로 저장. 기본 상태가 임시저장 |
| 수정 | 주소를 `둔산로 1234 (수정됨)`로 변경 | DB에 반영 |
| 확인 기록 | `이번에 확인한 항목`에서 `BASIC` 체크 | `BASIC`/`PHONE` 기록 1건 생성 |
| 확인자 | — | `verifiedBy = e2e-admin@example.test` — **세션 신원이 기록까지 전달됨** |
| 값 스냅샷 | — | 이름·주소·전화가 `verifiedValue`에 함께 저장(D-17) |
| 공개 전환 | `노출 상태`를 `공개`로 바꾸고 `저장` | `VISIBLE` |
| 공개 목록 반영 | `/ko/vets` | **4곳 → 5곳**, 신규 병원 표시 |
| 공개 상세 반영 | `/ko/vets/{id}` | 병원명·수정된 주소 표시 |
| 비공개 정보 | 공개 상세 응답 본문 | `adminNote`·`verifiedBy` **둘 다 없음** |

### 9-3. 일반 회원 차단

일반 회원 세션으로 `/ko/admin/vets`에 접근하면 `/ko/forbidden`으로 가고
**`관리자 권한이 필요합니다`** 화면이 나온다. 목록은 보이지 않는다. 비로그인은
`/ko/login`으로 간다(§8-3과 같은 가드).

### 9-4. 권한 표의 `—`는 무엇인가

§8-3 표의 빈 칸은 **미검증이 아니라 독립된 처리 경로가 없다는 뜻**이다. 코드로 확인했다.

- 병원 관련 서버 액션은 `createVetClinicAction`·`updateVetClinicAction` **둘뿐**이고,
  **같은 헬퍼를 거쳐 같은 `requireAdminAction()`** 가드를 탄다. 비로그인의 수정 거절은
  비로그인의 생성 거절과 같은 코드 경로다.
- 확인 기록은 **전용 엔드포인트가 없다.** create/update 트랜잭션 안에서
  `vetVerification.createMany`로 함께 쌓인다. 관리자의 확인 기록 추가는 §9-2의 수정
  단계에서 확인됐다.

따라서 빈 칸을 채우려고 테스트를 더 만들지 않았다.

### 9-5. 공개 실패 시 화면 안내 — 확인하고 고쳤다 (2026-09-13)

§9-5에 남겼던 "화면 안내가 보이지 않는다"는 관측을 **정확한 조건으로 재현해** 확인했다.
필수값을 모두 채우고 확인 기록 없이 `노출 상태`만 `공개`로 둔 상태다
(전송 payload에서 `visibility: "VISIBLE"`, `verifications: []` 확인).

**안내는 나오고 있었다. 다만 읽을 수 없었다.**

| | 수정 전 | 수정 후 |
|---|---|---|
| 제목 | `publishBlocked` | `공개 기준을 채우지 못해 저장하지 않았습니다. 아래를 채운 뒤 다시 저장하세요.` |
| 항목 | `basicVerification` | `기본 정보 확인 기록이 필요합니다 — '이번에 확인한 항목'에서 'BASIC'을 체크하세요.` |

서버가 `{ message: "publishBlocked", issues: ["basicVerification"] }`로 **무엇이 모자란지
이미 정확히 돌려주고 있었고**, 폼이 그 코드를 그대로 출력하고 있었다. 그래서 고친 것은
**표시 문구뿐이다** — `VetClinicForm`에 코드→문장 표를 두고 기존 오류 상자
(`border-destructive`)에 그대로 넣었다. 상자·색·위치는 바뀌지 않았고 `role="alert"`만 더했다.

**서버의 공개 기준(D-20)은 건드리지 않았다.** `findPublishBlockers`·`canPublishClinic`
모두 그대로다.

이 폼은 next-intl을 쓰지 않고 라벨을 한국어로 고정한다(`병원 등록`·`노출 상태` 등).
새 문구도 같은 방식이라 `/en/admin/vets/new`에서도 같은 한국어가 나온다 — 관리자 화면
전체의 기존 규칙이며 이번에 바꾸지 않았다.

### 9-6. 확인한 세 가지 (격리 DB, 관리자 세션)

| 확인 | 결과 |
|---|---|
| 부족한 조건을 화면에서 알 수 있는가 | **가능해졌다.** 무엇을 어디서 체크해야 하는지까지 문장으로 나온다 |
| 거절됐을 때 입력이 유지되는가 | **유지된다.** 병원명·주소·전화·노출 상태가 그대로 남아 다시 입력할 필요가 없다 |
| 조건을 채우면 공개되는가 | **된다.** `BASIC` 체크 후 저장하니 `VISIBLE`로 들어가고 확인 기록 1건이 쌓였으며, 공개 목록에 `병원 1곳`, 상세는 200으로 이름·주소가 나온다 |

거절된 시도는 DB에 **한 행도 남기지 않았다**(시도 중 `VetClinic` 0건 유지).

**검증 환경 주의.** `노출 상태` select가 저장 실패 후 `임시저장`으로 보이는 것을 관측했으나,
**제출 전에 이미 DOM과 React 상태가 어긋나 있었다** — 자동화 도구가 select의 DOM 값만
바꾸고 `onChange`를 발화시키지 못해 생긴 것이다. 제품 결함이 아니므로 고치지 않았다.
