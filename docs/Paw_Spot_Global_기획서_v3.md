## 1. 서비스 개요

### 서비스명

**Paw Spot Global**

> *명칭 검토 사항 (v2에서 유지)*: 서비스 범위가 한국 한정이므로 향후 "Paw Spot Korea" 등으로 변경을 검토할 수 있다. v3에서도 기존 명칭을 유지한다.

### 한 줄 소개

한국에 거주하거나 여행 중인 외국인 반려견 보호자가 반려견과 함께 갈 수 있는 음식점, 카페, 관광지를 영어로 쉽게 찾고, 방문 전 반드시 확인해야 할 조건을 명확하게 알 수 있는 반려견 동반 장소 안내 서비스.

### 핵심 메시지

> "Pet-friendly"라고 적힌 장소가 정말 갈 수 있는 곳인지, 방문 전에 꼭 확인해야 할 조건을 영어로 한눈에 보여준다.

### 차별화 한 줄

> 네이버·카카오 리뷰는 "갔다온 사람의 말", Paw Spot Global은 **"가기 전에 확인된 정보"**.

v3에서는 이 차별화를 **정책으로 강제한다.** 검증되지 않은 장소는 사용자 화면에 노출하지 않는다(§4 참조).

## 2. 기획 배경 (v2 유지)

포털, 지도 서비스, SNS에는 "애견 동반", "Pet-friendly"로 표시된 장소가 많지만 실제 방문하면 조건이 다른 경우가 많다.

- 실내는 불가능하고 야외 테라스만 가능한 경우
- 이동장이나 유모차가 있어야 입장 가능한 경우
- 소형견만 가능한 경우
- 중형견·대형견은 현장 상황에 따라 거절되는 경우
- SNS에는 가능하다고 되어 있지만 현재는 정책이 바뀐 경우

이 때문에 사용자는 방문 전에 매번 전화하거나 인스타그램 DM으로 확인해야 한다. 특히 외국인 사용자는 한국어로 문의하기 어렵고, 장소 설명이나 주의사항을 이해하기도 어렵다.

## 3. 문제 정의와 타깃 (v2 유지)

### 3-1. 문제

| 문제 | 설명 |
|---|---|
| "애견 동반 가능" 정보가 너무 넓음 | 실제로는 실내 가능, 야외만 가능, 이동장 필수 등 조건이 다름 |
| 조건 확인이 번거로움 | 전화, DM, 블로그 후기 확인을 사용자가 직접 해야 함 |
| 외국인은 정보 접근이 더 어려움 | 한국어 안내, 전화 문의, 매장 주의사항 이해가 어려움 |
| 현장 방문 실패 가능성 | 조건을 모르고 방문했다가 입장을 거절당할 수 있음 |
| 공공데이터만으로는 부족 | 반려동물 동반 유형은 알 수 있지만 세부 조건이 비어 있음 |
| 정책 변경 감지 불가 | 매장 정책이 바뀌어도 기존 정보가 그대로 노출됨 |

### 3-2. 타깃 사용자

**1차 타깃 — 한국에 거주하거나 장기 체류 중인 외국인 반려견 보호자 (영어 사용자)**

- 한국어가 익숙하지 않음
- 반려견과 카페, 음식점, 관광지를 찾고 싶음
- 포털·SNS 정보를 신뢰하기 어려움
- 전화 문의보다 영어 안내와 확인 문구를 선호함

**2차 타깃 — 한국 여행 중 반려견 동반 장소를 찾는 외국인 관광객**
단, MVP에서는 검역·항공·등록 절차는 다루지 않는다.

**부가 사용자 — 한국어 UI로 접근하는 한국인 보호자**
한국어 UI를 함께 제공하므로 자연 유입될 수 있으나, 한국인 특화 기능(주차, 혼잡도 등)은 우선순위로 두지 않는다.

### 3-3. 시장 근거 (v2 유지, 요약)

- 국내 체류 외국인 약 278만 명 (2025년 말 기준)
- 영어 UI로 접근 가능한 잠재 사용자 풀 약 30~35만 명
- 반려견 보유 + 동반 외출 + 앱 사용 의향을 고려한 활성 가능 풀 약 1~3만 명
- 경쟁 서비스(네이버 지도, 카카오맵, 다이닝코드, 국내 반려견 앱)는 모두 **영어 UI 미지원 또는 조건 비구조화**

## 4. 장소 검증 및 공개 정책 ★ v3 신설

이 절이 v3의 핵심이다. "가기 전에 확인된 정보"라는 약속을 운영 규칙으로 고정한다.

### 4-1. 공개 원칙

```
운영자 검증이 완료된 장소만 사용자 화면(홈 · 장소 목록 · 지도)에 공개한다.
검증되지 않은 장소는 관리자 후보 데이터로만 관리하며 사용자에게 노출하지 않는다.
```

- **검증 완료의 정의**: 운영자가 확인 방법(전화 / DM / 공식 홈페이지 / 방문)과 확인일을 기록한 검증 이력이 최소 1건 존재하는 상태.
- 후보 데이터는 수집·저장하되, 조건 입력과 검증이 끝나기 전까지는 어떤 사용자 화면에도 등장하지 않는다.
- 즐겨찾기에 담긴 장소도 공개 대상에서 빠지면 목록에서 사라진다.
- **검증 이력을 인위적으로 만들지 않는다** (결정 D-07). 기존에 검증 없이 공개되어 있던 장소가 있다면 노출에서 제외될 뿐, 임시 확인일이나 확인 방법을 생성해 공개 상태를 유지하지 않는다. 다시 공개하려면 실제로 확인해야 한다.

### 4-2. 장소 상태 정의

| 상태 | 뜻 | 사용자 노출 |
|---|---|---|
| 후보 (Candidate) | 원본·외부 데이터로 수집만 된 상태. 조건 미입력 | ❌ |
| 초안 (Draft) | 관리자가 조건을 입력 중이나 검증 이력 없음 | ❌ |
| 공개 (Published) | 조건 입력 + 검증 이력 1건 이상 + 노출 설정 ON | ✅ |
| 숨김 (Hidden) | 폐업·매장 요청 등으로 관리자가 내린 상태 | ❌ |

### 4-3. 조건 단위의 미확인 표시

장소가 공개되었더라도 개별 조건은 확인되지 않았을 수 있다. 이때 **추정하지 않는다.**

- 확인되지 않은 조건은 `Needs confirmation`으로 명시한다.
- 실내 동반 / 이동장·유모차 / 최대 허용 크기 — 이 **핵심 3조건 중 하나라도 미확인이면** 장소 요약 상태를 `Confirm before visiting`으로 표시한다.
- 미확인 조건을 "가능한 조건" 목록에 섞어 넣지 않는다.

### 4-4. 정보 신선도 정책

```
마지막 확인일로부터 90일이 지난 장소는 숨기지 않는다.
대신 `Recheck needed` 상태로 표시하고, 운영자 재확인 대기열에 올린다.
```

- 오래된 정보를 감추면 초기 데이터 규모에서 서비스가 비어 보이고, 사용자는 "정보가 없다"와 "정보가 오래됐다"를 구분할 수 없다. 노출하되 신선도를 정직하게 알리는 쪽을 택한다.
- 재확인 우선순위: ① 사용자 신고 누적 ② 90일 경과 ③ 정기 순회

**임계값은 90일 하나만 사용한다** (결정 D-02).

- 이전에 사용하던 8주(56일) "정보 노후" 경고 임계는 폐기한다. 56일과 90일은 34일 차이로, 사용자가 두 상태를 구분해 다르게 행동할 근거가 없다.
- 중간 단계 경고를 추가하지 않는다. 경고가 흔해지면 어떤 것도 강조되지 않는다.
- `DESIGN.md` v1.2에 동일 기준이 반영되어 있다.

### 4-5. 데이터 운영 단계 (v2 유지)

| 단계 | 규모 | 방식 |
|---|---|---|
| Phase 1 | ~50곳 | 운영자 100% 검증 (전화 / DM / 홈페이지 / 방문). 장소당 평균 10~15분 |
| Phase 2 | 50~150곳 | 매장 사장 직접 입력(B2B) + 운영자 검수 |
| Phase 3 | 150곳~ | 사용자 신고 누적 기반 자동 재확인 트리거 + 운영자는 분쟁 조정 집중 |

## 5. MVP 목표와 범위

### 5-1. MVP 목표

```
외부 원본 데이터로 후보 장소를 확보하고,
운영자 검증을 거쳐 방문 전 핵심 조건이 구조화된 장소만 공개하며,
지도 중심 화면에서 영어로 "내 반려견이 갈 수 있는지"를 판단하게 한다.
```

### 5-2. MVP 성공 기준

| 기준 | 목표 |
|---|---|
| 검증 완료 공개 장소 | **대전 기준 30~50곳** |
| 핵심 3조건 확인율 | 공개 장소의 90% 이상에서 실내·이동장·크기 조건이 `Needs confirmation`이 아닐 것 |
| 베타 사용자 | 대전 거주·체류 외국인 커뮤니티 대상 가입 의향 30명 이상 |
| 상세 페이지 평균 체류 | 90초 이상 |

### 5-3. 핵심 검증 가설 (v2 유지)

| 가설 | 검증 방법 |
|---|---|
| 사용자는 "애견 동반 가능"보다 세부 조건을 더 원한다 | 사용자 인터뷰, 프로토타입 반응 |
| 외국인 사용자는 영어 조건 요약을 필요로 한다 | 영어 UI 테스트 5~10명 |
| 실내·이동장·크기 3조건이 가장 유용하다 | 조건별 클릭·체류 로깅 |
| 검증 데이터가 신뢰도를 높인다 | 확인일·확인 방법 노출 후 만족도 측정 |
| 시드 30~50곳 검증으로 초기 만족도를 확보할 수 있다 | 베타 NPS |

## 6. 서비스 핵심 기능

### 6-1. 홈 — 카테고리 탐색

홈의 목적은 소개가 아니라 **첫 화면에서 실제 후보 장소를 보여주는 것**이다.

- 카테고리 탭: **All / Restaurants / Cafes / Attractions**
  - `Attractions`는 v2의 "여행지"에 해당한다. 관광지·공원·산책 가능 장소를 포함한다.
  - 숙소와 기타 카테고리는 탭에 포함하지 않는다.
- 각 탭은 해당 카테고리의 **실제 공개 장소 카드**와 총 개수를 보여준다.
- 카드에는 즐겨찾기 토글을 둔다.
- 탭 전환 시 **로딩 · 빈 상태 · 오류 상태**를 모두 처리한다. 오류에는 재시도 수단을 둔다.
- 각 탭에서 `View all`로 장소 탐색 화면(해당 카테고리 필터 적용)으로 넘어간다.

**장소 탐색 섹션은 홈에 하나만 둔다.** v2 기준의 "Featured / Recent Places" 별도 그리드는 카테고리 탭과 같은 데이터를 다른 형태로 반복 노출하므로 v3에서는 통합한다. 홈에서 같은 장소가 두 번 등장하지 않아야 한다.

홈의 나머지 구성:

```
Hero          — 서비스 한 줄 + 검색 + 내 주변
Category Tabs — 카테고리별 공개 장소 (유일한 장소 탐색 섹션)
What to check — 방문 전 확인해야 할 항목 안내
Footer        — 면책 문구
```

### 6-2. 지도 중심 장소 탐색

탐색 화면의 기본 축은 **지도**다. 목록만으로는 "내 주변"이라는 판단이 서지 않는다.

**데스크톱 (넓은 화면)**

```
[ 장소 목록 ] [ 선택 장소 미리보기 ] [ 지도 ]
```

- 세 영역은 하나의 선택 상태를 공유한다.
- 카드 hover → 지도 마커 강조
- 카드 선택 → 미리보기 열림 + 마커 선택
- 마커 선택 → 미리보기 열림 + **해당 카드가 목록에서 보이도록 스크롤**
- 선택한 장소가 없으면 미리보기 영역을 접고 지도를 넓게 표시한다.
- 중간 폭에서는 미리보기를 지도 위 오버레이로 띄워 지도 폭을 지킨다.

**모바일**

- 지도를 배경으로 두고 **3단계 Bottom Sheet**를 사용한다.

| 단계 | 내용 |
|---|---|
| 1단계 (요약) | 결과 개수 + 목록 열기 |
| 2단계 (목록) | 검색·카테고리·필터·정렬 + 장소 카드 목록 |
| 3단계 (선택) | 선택한 장소 미리보기 |

- 목록과 지도를 오가도 필터·선택 상태를 유지한다.
- 모바일을 데스크톱 3분할의 축소판으로 만들지 않는다.

**탐색 범위 정책**

- MVP 데이터 규모(수십 곳)에서는 **전체 공개 장소를 한 번에 조회하는 방식을 임시 허용**한다. 이 단계에서 반경을 좁히면 결과 0건이 빈번해 오히려 해롭다.
- **전국 확장 이전에** 지도 Bounds 기반 `이 지역 검색`과 서버 페이징을 반드시 구현한다. 이는 선택이 아니라 확장 전 필수 선행 조건이다.

**서비스 범위 안내와 기본 지도 중심 (결정 D-11)**

초기에는 대전만 공개하므로(§9), 다른 지역 사용자가 서비스를 열면 주변에 장소가 하나도 없다. 이 상태를 고장이 아니라 **현재 서비스 범위**로 이해하게 만든다.

- **기본 지도 중심을 대전으로 한다.** 위치 권한이 없거나 거부된 사용자에게는 대전 지도를 보여준다.
- 초기 서비스 범위가 대전임을 알리는 **안내 배너**를 둔다.
- 사용자 위치가 서비스 범위 밖이면 **`현재 대전 지역만 지원합니다`** 안내와 함께 **`대전 장소 보기`** 버튼을 제공한다. 사용자가 허용한 위치를 말없이 무시하지 않고, 이동 여부를 사용자가 선택하게 한다.
- **빈 상태를 두 종류로 분리한다.** 원인이 다르면 다음 행동도 달라야 한다.

| 빈 상태 | 원인 | 안내와 다음 행동 |
|---|---|---|
| 서비스 범위 밖 | 사용자 위치에 서비스 지역이 없음 | `현재 대전 지역만 지원합니다` + `대전 장소 보기` |
| 필터 결과 0건 | 조건을 좁혀 결과가 사라짐 | 조건이 맞는 곳이 없다는 안내 + **`필터 초기화`** |

### 6-3. 선택 장소 패널과 상세 페이지의 역할 분리

| 화면 | 목적 | 담는 것 | 담지 않는 것 |
|---|---|---|---|
| **선택 장소 미리보기 패널** | 빠른 방문 가능성 판단 | 장소명·카테고리·거리·전체 주소, 동반 조건 전체, 주의사항, 확인일·확인 방법 | 대표 이미지, 운영시간, 연락처 |
| **전체 상세 페이지** | 최종 확인과 실행 | 대표 이미지, 방문 전 확인 조건 전체, 검증 정보, 연락처, 운영시간, 길찾기·공유, 신고 | — |

- 미리보기의 **Primary Action은 `상세 보기`** 다. 미리보기의 목적은 상세로 이어주는 것이다.
- **`길찾기`는 Secondary Action**으로 유지한다. 위치 정보가 없으면 해당 액션을 노출하지 않는다.
- 미리보기는 카드보다 반드시 많은 정보를 보여준다. 카드와 같은 내용만 반복하면 패널을 열 이유가 없다.

### 6-4. 방문 전 필수 확인 조건

서비스의 본체다. "반려견 동반 가능"이라고 쓰지 않고 조건을 구조화해 보여준다.

| 항목 | 값 |
|---|---|
| 실내 동반 | 가능 / 야외·테라스만 / 일부 구역만 / 불가 / 확인 필요 |
| 이동장·유모차 | 불필요 / 실내에서만 필요 / 항상 필요 / 확인 필요 |
| **최대 허용 크기** | 소형견까지 / 중형견까지 / 대형견까지 / 확인 필요 |
| 목줄 | 필수 / 불필요 / 일부 구역 / 확인 필요 |
| 입마개 | 필수 / 불필요 / 조건부 / 확인 필요 |
| 견종 제한 | 자유 입력 |
| 준비물 | 배변봉투 등 |
| 주의사항 | 자유 입력 |
| 확인일 · 확인 방법 | 전화 / DM / 공식 홈페이지 / 방문 |

**v2에서 바뀐 점**

- v2의 "소형견 가능 / 중형견 가능 / 대형견 가능"을 **복수 선택이 아닌 단일 상한(`최대 허용 크기`)** 으로 바꾼다. 실제 매장 정책은 "소형만" "중형까지"처럼 상한으로 표현되며, 이렇게 두어야 등록된 반려견 크기와의 비교가 자명해진다.
- v2의 "이동장 필수 여부"와 "유모차 가능 여부"를 하나의 3단계 정책으로 합친다. 매장은 대개 둘을 같은 규칙으로 다룬다.
- 목줄과 입마개를 준비물 목록에서 꺼내 독립 조건으로 승격한다. 준비물이 아니라 입장 조건이기 때문이다.

**예방접종 증빙**

- 매장 정책 필드로 저장할 수 있다.
- **반려견 프로필이나 자동 방문 가능 판정에는 사용하지 않는다.**
- 값이 `확인 필요`이면 사용자 화면에서 기본적으로 숨긴다. 일반 카페·음식점에서 대부분 무의미한 줄이 되기 때문이다.
- 숙소의 예방접종·추가 요금·동반 두수 조건은 조건 구조 자체가 다르므로 **P2에서 별도 모델로 설계**한다.

**조건 필터에서의 미확인 값 처리 (결정 D-03, D-12)**

- "실내 가능", "이동장 불필요"처럼 **특정 조건을 충족한 곳을 찾는 필터는 확인된 일치 값만 포함**한다. 미확인(`확인 필요`) 장소는 자동으로 제외된다.
- 사용자가 그 조건을 근거로 걸렀는데 실제로는 확인되지 않은 곳이 섞여 나오면, 서비스가 가장 크게 신뢰를 잃는 지점이 된다.
- 이는 조건 표시 원칙(§4-3)과 같은 규칙이다. 확인되지 않은 조건은 어디에서도 충족된 것처럼 다루지 않는다.
- 실내 조건에만 있던 **`확인 필요 제외` 옵션은 삭제**한다. 모든 긍정 조건 필터가 같은 규칙으로 동작하므로 별도 옵션이 필요 없다.
- **전역 "확인된 조건만 보기" 토글은 MVP에 넣지 않는다.** 필터가 이미 확정값만 통과시키므로 중복이다. 필요성이 확인되면 이후 단계에서 다룬다.
- 예외: 반려견 크기 필터는 미확인 장소를 목록에서 지우지 않는다. 크기 미확인은 `Size limit unconfirmed`로 별도 단언되므로(§6-5), 목록에서 제거하면 오히려 정보를 감추게 된다.

**운영시간 (결정 D-04)**

- 요일별 영업 시작·종료 시간을 구조화해 저장하고, 영어·한국어 UI 모두에서 자동으로 표시한다.
- 브레이크타임처럼 정형화하기 어려운 사항은 **짧은 운영시간 메모 한 줄**로 함께 남긴다.
- 운영시간을 자유 텍스트로만 받지 않는다. 운영자가 한국어로 적으면 외국인 사용자가 읽을 수 없어 서비스 전제가 무너진다.

**디스클레이머** (모든 상세 화면)

```
This information was verified on [date] through [method].
Store policies may change. We recommend confirming with the store
before your visit, especially for special circumstances.
```

### 6-5. 대표 반려견 1마리

MVP에서는 사용자당 **대표 반려견 1마리**만 등록한다.

**입력 항목**: 이름 / 크기(소형·중형·대형) / 견종(선택)

**활용**

- 장소 탐색 화면의 **크기 필터 기본값**으로 자동 적용된다.
- 장소 카드와 미리보기에 **방문 가능 여부를 한 문장으로 단언**한다.
  - `Your dog can visit` — 최대 허용 크기 ≥ 등록 크기
  - `Too large for this place` — 허용 크기 미만
  - `Dogs not allowed here` — 동반 불가
  - `Size limit unconfirmed` — 허용 크기 미확인
- 반려견 프로필이 없으면 **판정을 표시하지 않는다.** 추측으로 단언하지 않는다.
- 판정은 결론만 담고, 근거가 되는 조건은 바로 아래에 그대로 보여준다.

**MVP 이후로 이동**

- 여러 마리 등록과 개별 CRUD
- 비회원 localStorage 프로필 저장
- 체중 기반 판정, 예방접종 기반 필터 (v2와 동일하게 제외 유지)

### 6-6. 즐겨찾기

- 로그인 사용자가 장소를 저장하고 별도 목록에서 다시 볼 수 있다.
- 비로그인 상태에서 즐겨찾기를 시도하면 현재 맥락을 보존한 채 로그인으로 유도한다.
- 즐겨찾기 목록은 장소 목록과 같은 카드 컴포넌트를 재사용한다.

### 6-7. 영어 중심 다국어 UI

| 언어 | MVP | 근거 |
|---|---|---|
| 영어 | 포함 (기본) | 1차 타깃 언어 |
| 한국어 | 포함 (보조) | 한국인 부가 유입, 운영자 입력용 |
| 일본어 / 중국어 | P2 이후 | 1인 운영 부담 대비 효과 낮음 |

- 영어 UI에서는 영문 장소명을 앞에, 한국어명을 보조로 표시한다. 한국어 UI는 반대.
- 장소명을 자동 번역하지 않는다. 관리자가 영문명을 입력한 경우에만 사용한다.
- 번역되지 않은 정보를 번역된 사실처럼 보이게 하지 않는다.

### 6-8. 정보 오류 신고

구조화 리뷰보다 **먼저** 구현한다.

- 사용자가 상세 페이지에서 "정보가 잘못됐어요"를 신고할 수 있다.
- 사유: 정보 오류 / 폐업 / 정책 변경 / 기타
- 이 기능이 §4-4 재확인 정책의 실행 수단이다. 리뷰 없이도 데이터 보정 루프를 닫을 수 있다.

**접수 정책 (결정 D-09)**

- **비로그인 사용자도 신고할 수 있다.** 이 기능의 목적은 사용자 참여가 아니라 재검증 신호 확보다. 초기 사용자 규모에서 로그인 벽을 두면 신호 자체가 모이지 않는다.
- 도배 방지를 위해 **접수 제한(Rate Limit)** 을 둔다. 동일 사용자·동일 장소 기준으로 일정 시간 내 중복 접수를 막는다.
- **신고는 장소 상태를 자동으로 바꾸지 않는다.** 재확인 대기열에만 쌓이고, 운영자가 검토한 뒤에만 반영된다. 도배가 발생해도 최악의 결과는 "운영자가 대기열을 비우는 일"에 그친다.
- 신고 누적은 재확인 **우선순위**를 올리는 신호로만 사용한다.

```
[홈]
  카테고리 탭에서 Cafes 선택 → 공개된 카페 카드 확인

        │
        ▼
[카드 선택 또는 마커 선택]
  미리보기 패널 열림 (데스크톱) / Bottom Sheet 3단계 (모바일)
  방문 가능 여부 단언 + 조건 전체 + 확인일·확인 방법

[상세 보기]  ← 미리보기의 Primary Action
  방문 전 확인 조건 전체 · 검증 정보 · 연락처 · 운영시간
  길찾기 / 공유 / 즐겨찾기 / 신고
```

### 7-2. 대표 반려견 등록 흐름

```
[헤더] My Dog
   → 비로그인이면 로그인(Google) 후 복귀
   → 이름 · 크기 · 견종 입력 후 저장
   → 이후 장소 탐색에서 크기 필터가 자동 적용되고
     각 장소에 방문 가능 여부가 단언됨
```

### 7-3. 운영자 데이터 흐름

```
[후보 수집]  외부 원본 데이터 Import (중복 방지)
      ▼
[관리자 검토]  후보 목록에서 대상 선택
      ▼
[조건 입력]  실내 · 이동장 · 최대 크기 · 목줄 · 입마개 · 주의사항

      ▼
[재확인]  90일 경과 또는 신고 누적 → Recheck needed → 재검증
```

## 8. 데이터 전략

### 8-1. 후보 데이터 수집 (TourAPI)

MVP에서 확보해야 할 것은 **완성된 관리자 대시보드가 아니라, 후보 장소를 반복해서 가져와 검증된 공개 장소로 전환할 수 있는 파이프라인**이다.

```
TourAPI 또는 원본 데이터
→ 중복 방지 Import
→ 관리자 검토
→ 조건 입력 및 검증
→ 공개 Place 전환
```

**MVP 최소 범위**

- 외부 원본에서 장소명·주소·좌표·대표 이미지·분류를 가져온다.
- 같은 원본 식별자는 두 번 들어오지 않는다(중복 방지).
- 가져온 데이터는 **후보 상태**로만 저장되며 사용자에게 노출되지 않는다.
- 관리자가 후보를 열어 조건을 입력하고 검증을 기록하면 공개 대상이 된다.
- 이 파이프라인은 스크립트나 최소 화면 어느 쪽으로 구현해도 무방하다. 반복 실행이 가능하기만 하면 된다.

**P1으로 이동**

- 관리자 후보 목록 대시보드(필터·일괄 처리·Reject 관리)
- 후보에서 등록 폼으로의 자동 채움
- 정기 동기화 스케줄링

### 8-2. 운영자 검증 데이터

- 조건 항목 전체(§6-4)
- 확인 방법: 전화 / 인스타그램 DM / 공식 홈페이지 / 방문 확인 / 사용자 신고 기반 재확인
- 확인일과 확인자
- 검증은 이력으로 쌓는다. 재검증 시 이전 기록을 덮어쓰지 않는다.

### 8-3. 사용자는 원본이 아니라 가공된 데이터를 본다

외부 원본은 후보 확보용이다. 사용자가 보는 것은 운영자가 구조화하고 검증한 조건 데이터다. 단순 공공데이터 목록 서비스가 아니라 **검증 조건 중심의 안내 서비스**임이 서비스의 존재 이유다.

## 9. 초기 서비스 지역 (결정 D-08)

```
초기에는 대전만 공개한다.
서비스가 안정화된 뒤 다른 지역으로 단계적으로 확장한다.
```

### 9-1. 단계별 범위

| 단계 | 지역 | 조건 |
|---|---|---|
| **1단계 (현재)** | **대전** | 검증된 장소 30~50곳 확보 후 공개. 대전 이외 지역의 장소는 검증하지 않고 공개하지도 않는다. |
| 2단계 | 서울 (이태원·한남동 우선) | 1단계 안정화 조건(§9-3) 충족 후 착수 |
| 3단계 | 전국 | **P2.** §6-2의 Bounds 기반 `이 지역 검색`과 서버 페이징이 반드시 선행되어야 한다. |

### 9-2. 대전을 먼저 택한 이유

- **검증 품질**: 운영자가 직접 방문해 확인할 수 있는 유일한 지역이다. 전화·DM 확인만으로는 잡히지 않는 조건(실제 실내 좌석 배치, 테라스 상태, 현장 거절 관행)을 1단계에서 잡아 검증 프로토콜을 확정한다.
- **검증 속도**: 장소당 확인 시간이 짧아 30~50곳 확보가 빠르다.
- **운영 부담**: 매장 재확인, 정보 수정 요청 대응, 신고 처리까지 한 지역 안에서 닫힌다.

### 9-3. 확장 트리거 (2단계 착수 조건)

1. 대전 검증 완료 장소 30곳 이상, 핵심 3조건 확인율 90% 이상
2. 재확인 루프 1회 이상 완주 (90일 경과 장소를 실제로 재검증해 본 경험)
3. 신고 접수 → 운영자 검토 → 반영까지의 처리 흐름이 실제로 동작
4. 홈·탐색·상세의 로딩/빈/오류 상태 처리 완료

### 9-4. 감수하는 리스크

이 순서는 **검증 품질을 먼저 확보하고 시장을 나중에 만나는** 선택이다. 다음을 인지한 상태로 진행한다.

- 1차 타깃(영어권 체류 외국인)의 밀집도는 서울이 압도적으로 높다. 대전 단독 공개 기간에는 **활성 사용자 수와 관련한 검증 가설(§5-3)을 충분히 검증하기 어렵다.**
- 이 기간의 성공 기준은 사용자 수가 아니라 **데이터 품질과 운영 루프의 완주**로 본다. 사용자 수 지표(§15)는 2단계 진입 후부터 유효한 것으로 취급한다.
- 대전에도 대학·연구단지를 중심으로 외국인 체류자가 있으므로 초기 사용자 피드백 자체는 확보 가능하다고 본다. 다만 규모는 서울 대비 작다.

### 9-5. 지역 제한을 적용하는 방식

**공개 대상 제한**은 코드가 아니라 운영 규칙으로 강제한다. 별도의 지역 필드나 필터를 만들지 않는다. 공개 여부는 이미 "운영자 검증 완료"로 통제되므로(§4-1), 운영자가 대전 장소만 검증·공개하면 목표가 달성된다.

**사용자 안내**는 코드 작업이 필요하다. 기본 지도 중심, 서비스 범위 배너, 범위 밖 안내는 §6-2(결정 D-11)에 정의되어 있다.

지역 필드는 2단계(복수 지역 동시 공개) 진입 시점에 도입한다.

## 13. 법적 면책 및 리스크 관리 (v2 유지)

### 13-1. 디스클레이머

모든 장소 상세 화면에 영어와 한국어로 표시한다.

```
This information was verified on [date] and may change without notice.
Paw Spot Global does not guarantee admission. Please confirm with the
store before your visit, especially for special circumstances such as
large breeds, group bookings, or peak hours.
```

### 13-2. 약관 핵심 조항

- 본 서비스는 매장의 입장 가능 여부를 보장하지 않으며, 안내 정보에 근거한 방문 결과에 책임을 지지 않는다.
- 모든 정보는 확인일 기준이며 매장 정책 변경에 따라 달라질 수 있다.
- 사용자가 부정확한 정보를 발견하면 신고를 통해 재확인을 요청할 수 있다.

### 13-3. 매장 측 요청 대응

- 정보 수정·등록 해제 요청은 영업일 기준 3일 이내 처리
- 잘못된 정보로 인한 매장 피해 신고 채널 운영

## 15. 출시 후 검증 지표

**1단계(대전 단독 공개) — 데이터·운영 지표 중심**

§9-4에 따라 이 기간에는 사용자 수 지표를 성공 기준으로 쓰지 않는다.

| 지표 | 목표 |
|---|---|
| 검증 완료 공개 장소 | 30~50곳 |
| 핵심 3조건 확인율 | 90% 이상 |
| 재확인 루프 완주 | 90일 경과 장소 재검증 1회 이상 |
| 신고 → 운영자 검토 → 반영 | 영업일 3일 이내 90% |
| 상세 페이지 평균 체류 | 90초 이상 |
| 사용자가 가장 자주 확인하는 조건 | 로깅으로 측정, 조건 우선순위 조정에 반영 |

**2단계(서울 확장) 이후 — 사용자 지표**

| 지표 | 목표 |
|---|---|
| 월간 활성 사용자 | 확장 3개월 후 200명 |
| 7일 재방문율 | 20% 이상 |

**Phase 2(운영 모델 전환) 진입 조건**

- 검증 완료 장소 30곳 이상
- §9-3의 확장 트리거 4개 충족
- 월간 활성 사용자 100명 이상 (2단계 진입 후 측정)
- 매장 사장 입력 채널 의향 표명 5건 이상
