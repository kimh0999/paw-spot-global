# 없는 상세 페이지가 HTTP 200을 돌려주는 이유 — 진단 (2026-09-13)

없는 ID·비공개 데이터의 상세 URL이 **404 화면을 보여주면서 상태 코드는 200**이다.
이것이 구현 결함인지 프레임워크의 문서화된 동작인지 실측으로 갈랐다.

대상 버전: **Next.js 16.3.5** (이 저장소에 설치된 것). 문서는 참고만 하고 판정은 실행 결과로 했다.

## 1. 결론

**문서화된 스트리밍 동작이다. 제품의 예외 처리·렌더링 결함이 아니다.**

`loading.tsx`가 만드는 Suspense 경계가 스트리밍을 켠다. 응답 헤더(200)가 먼저 나간 뒤에
페이지 컴포넌트가 `notFound()`를 던지므로, 이미 확정된 상태 코드를 바꿀 수 없다.

## 2. 근거 — 재현 조건

| 조건 | `/ko/vets/{없는 ID}` | `/ko/places/{없는 ID}` | `/ko/places/{공개}` |
|---|---|---|---|
| 현재 상태 (`loading.tsx` 3개 있음) | 200 | 200 | 200 |
| `(public)/loading.tsx` + `places/[id]/loading.tsx` 제거 | **404** | 200 | 200 |
| 위 + `places/loading.tsx`까지 제거 | **404** | **404** | 200 |

- 병원은 `(public)/loading.tsx` **그룹 경계**만 없애도 404가 된다.
- 장소는 `places/loading.tsx`가 **하위 세그먼트(`places/[id]`)까지** 감싸므로 그것까지
  없애야 404가 된다.
- 어느 경우에도 **정상 공개 페이지는 200 그대로**다.

경계를 없애면 상태 코드가 바로잡힌다는 것이, 원인이 스트리밍 경계라는 직접 증거다.

## 3. 배제한 가설

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 예외 처리가 `notFound()`를 삼킨다 | 두 상세 페이지의 `try` 블록 수 | **0개.** 삼킬 코드가 없다 |
| `notFound()`가 호출되지 않는다 | 경계 제거 후 상태 | 404가 나온다 → 호출되고 있다 |
| 라우팅 자체가 404를 못 만든다 | `/ko/no-such-route` | **404.** 경계 밖이라 정상 |
| `generateMetadata`에서 `notFound()`를 부르면 고쳐진다 | 실제로 바꿔 빌드·측정 | **여전히 200.** 효과 없어 원복함 |

마지막 항목이 중요하다. `generateMetadata`는 shell flush 전에 돌므로 상태를 잡을 것으로
기대했으나 **이 버전에서는 바뀌지 않았다.** 추정으로 두지 않고 실측해 기각했다.

## 4. 실제 영향

| 항목 | 상태 |
|---|---|
| 사용자가 보는 화면 | **정상.** 404 UI가 스트리밍 페이로드로 전달돼 브라우저가 그린다 |
| 비공개 데이터 노출 | **없음.** 숨김·임시저장은 이름조차 나오지 않고 `adminNote`·`verifiedBy`도 없다. JSON-LD도 생성되지 않는다 |
| 검색 색인 | 초기 HTML에 `noindex`가 **들어 있다** |
| 남는 위험 | JS를 실행하지 않는 크롤러에게는 **본문이 빈 200**으로 보인다 (soft 404). 색인은 `noindex`가 막지만 크롤 예산 낭비와 진단 도구의 오탐은 남는다 |

**`noindex`가 있다고 해서 전부 해결된 것은 아니다.** 상태 코드로 말해야 할 것을 메타 태그로
말하고 있는 상태이며, 위 표의 마지막 줄이 그 대가다.

## 5. 해결 (2026-09-13)

**상세 라우트를 `(public)` 그룹 밖으로 옮겨 해결했다.** 로딩 UI는 그대로 둔다.

### 5-1. 바꾼 것

```
[locale]/(public)/places/[id]/  →  [locale]/(detail)/places/[id]/
[locale]/(public)/vets/[id]/    →  [locale]/(detail)/vets/[id]/
[locale]/(detail)/places/[id]/loading.tsx  삭제
```

`(detail)`은 `(public)`의 **형제 그룹**이라 `(public)/loading.tsx`의 Suspense 경계
바깥이다. 라우트 그룹은 URL에 나타나지 않으므로 **기존 URL·ko/en 라우팅은 그대로다**
(빌드 출력의 `/[locale]/places/[id]`·`/[locale]/vets/[id]` 확인).

공개 조건 판정과 접근 권한 코드는 **건드리지 않았다.** 페이지가 `notFound()`를 부르는
지점도 그대로이며, 그 앞에 스트리밍 경계가 없어졌을 뿐이다.

### 5-2. 하지 않은 것

- 전역 로딩 UI 일괄 제거 — `(public)/loading.tsx`와 `places/loading.tsx`는 **그대로 있다.**
  후자는 이제 목록만 감싼다(상세가 그룹 밖으로 나갔으므로).
- 모든 요청에 DB 조회 추가 — 조회 횟수는 변하지 않았다. 판정은 기존과 같은 자리에서 한다.
- 프레임워크 버전 변경 — Next 16.3.5 그대로.
- `layout.tsx`로 판정을 올리는 방안은 **효과가 없어 기각했다.** 상위 `(public)/loading.tsx`
  경계가 이미 flush하기 때문이다(실측).

### 5-3. 결과

| 경로 | ko | en |
|---|---|---|
| 장소 상세 — 공개 | 200 | 200 |
| 장소 상세 — `DRAFT` | **404** | **404** |
| 장소 상세 — 없는 ID | **404** | **404** |
| 병원 상세 — 공개 | 200 | 200 |
| 병원 상세 — 숨김·임시저장 | **404** | **404** |
| 병원 상세 — 없는 ID | **404** | **404** |

정상 공개 상세는 metadata·JSON-LD가 그대로 나오고, 404 응답에는 **JSON-LD가 없고**
`noindex`가 붙으며 비공개 정보(`adminNote`·`verifiedBy`·병원명)는 **어느 응답에도 없다.**

목록·홈은 200이고 로딩 스켈레톤도 그대로다.

### 5-4. 남은 것 — 상세의 로딩 스켈레톤

상세 페이지는 이제 경계가 없어 **데이터가 올 때까지 응답을 시작하지 않는다.** 초기
스켈레톤이 사라진 대신 상태 코드가 정확해졌다.

측정값(로컬 → Supabase): 상세 TTFB **약 75~100ms**. 이 정도면 스켈레톤 없이도 체감이
나쁘지 않다고 보아 그대로 두었다.

더 느려지면 **존재 확인 이후의 무거운 부분만** 페이지 안에서 `<Suspense>`로 감싸는 방법이
있다. 그 경우에도 경계가 `notFound()` 뒤에 오므로 상태 코드는 유지된다. 지금은 감쌀 만큼
무거운 구역이 없어 넣지 않았다.

### 5-5. 404 본문은 여전히 스트리밍으로 온다

상태 코드는 404지만 초기 HTML 본문은 비어 있고 404 UI는 RSC 페이로드로 전달된다.
**이번 변경 전과 같은 동작이며**, 브라우저에서는 `찾을 수 없는 페이지입니다` 화면이
정상적으로 그려지는 것을 확인했다. 크롤러에게는 이제 **상태 코드 404가 먼저 도달**하므로
soft 404 문제는 해소됐다.
