## 1. React 18 유지 판단 — 정정했다

### 이전 판단

> `next@15.5.25`의 `peerDependencies`가 `react: "^18.2.0 || ^19.0.0"`이므로 React 18.3.1을 유지한다.

**이 근거는 틀렸다.** peerDependencies 범위는 Pages Router까지 포괄하는 **패키징 표기**이지
App Router의 지원 조건이 아니다. 빌드가 통과한 것도 근거가 되지 못했다.

### 확인한 사실

**공식 문서** (`nextjs.org/docs/15/app/guides/upgrading/version-15`, 문서 표기 버전 15.5.25):

> ## React 19
> * The minimum versions of `react` and `react-dom` is now 19.
> * `useFormState` has been replaced by `useActionState`. …deprecated and will be removed in a future release.
> * **Good to know:** If you are using TypeScript, ensure you also upgrade `@types/react` and `@types/react-dom`.

**이 저장소는 App Router 전용이다** — `pages/` 디렉터리가 없다. Pages Router용 예외가 적용될 여지가 없다.

**런타임 실측** — Next는 자기 React를 따로 들고 있다.

| 확인 | 결과 |
|---|---|
| `next/dist/compiled/react` 번들 버전 | `19.2.0-canary-0bdb9206-20250818` |
| 업그레이드 **전** 클라이언트 청크의 React 버전 문자열 | `19.2.0-canary…` 7건 + **`18.3.1` 2건** |
| `18.3.1`이 들어 있던 청크 | `framework-*.js` 단 한 개 |
| App Router 페이지가 `framework-*.js`를 쓰는가 | **쓰지 않는다** (`app-build-manifest.json` 전수 확인 결과 0건) |

즉 **App Router는 이미 Next가 번들한 React 19로 돌고 있었고**, 설치된 React 18.3.1은
App Router가 불러오지 않는 Pages Router 대비 청크와 **TypeScript 타입**에만 쓰이고 있었다.
타입이 런타임을 설명하지 못하는 상태였다.

### 조치

| 패키지 | 전 | 후 |
|---|---|---|
| `react` · `react-dom` | 18.3.1 | **19.2.8** |
| `@types/react` | 18.3.29 | **19.2.18** |
| `@types/react-dom` | 18.3.7 | **19.2.7** |

**19.3.0이 아니라 19.2.x를 골랐다.** Next 15.5.25가 번들한 React가 19.2 계열이라,
설치본의 minor를 런타임과 맞추는 쪽이 예상 밖 차이를 줄인다. `react`·`react-dom`은
`npm audit` 기준 공지가 **0건**이라 어느 19.x를 고르든 보안 차이는 없다.

**호환성**: `next-auth@5.0.0-beta.32`(`^18.2.0 || ^19.0.0`) · `next-intl@4.12.0`(`… || ^19.0.0`) ·
`radix-ui@1.4.3`(`… || ^19.0`) · `lucide-react@1.16.0` · `sonner@2.0.7` 모두 React 19를 받는다.
중복 설치 없음(전부 `deduped`).

**`useFormState` → `useActionState`** — 3개 파일(`PlaceForm` · `VetClinicForm` · `DogForm`).
React 19에도 `useFormState`는 남아 있지만 렌더마다 다음 경고를 낸다:
`ReactDOM.useFormState has been renamed to React.useActionState.`
`VetClinicForm.tsx`에 있던 "React 18이라 useActionState(19) 대신 …" 주석도 사실과 달라져 고쳤다.

**업그레이드 후 실측**: 클라이언트 청크의 React 문자열이 `19.2.8` / `19.2.0-canary`만 남았고
`18.3.1`은 0건. 브라우저 10개 화면에서 **하이드레이션 오류 0건**.

**Next 16 전환은 이번 범위가 아니다.** 15.x는 Maintenance LTS이고 정책상 2026-10-21경
종료되므로 별도 과제로 남긴다(`next lint` 제거 대응 포함).

## 2. 이미지 최적화 경로와 SSRF — 설명을 정정했다 (코드는 그대로)

### 이전 설명

> `remotePatterns`가 없어 **이미지 최적화 경로 자체가 구성되지 않는다.**

**틀렸다.** `/_next/image` 엔드포인트는 설정과 무관하게 **항상 존재하고 살아 있다.**

### 실측 (production 빌드, `next start`)

| 요청 | 응답 |
|---|---|
| `?url=https://example.com/a.jpg` | **400** `"url" parameter is not allowed` |
| `?url=http://127.0.0.1:55432/` | **400** |
| `?url=http://169.254.169.254/latest/meta-data/` | **400** |
| `?url=/favicon.ico` | **200** — 서버가 실제로 이미지를 읽어 처리한다 |
| `?url=/../../../etc/passwd` | 400 |
| `?url=javascript:alert(1)` | 400 |

즉 **서버 측 이미지 처리 경로는 존재하며, 로컬 경로에 한해 동작한다.**
외부 호스트가 막히는 이유는 "경로가 없어서"가 아니라 **`remotePatterns` 기본값이 비어 있어서**다
(공식 문서: "allow images from specific external paths and **block all others**").

### 구분해야 할 두 가지

| 질문 | 답 |
|---|---|
| `thumbnailUrl`이 브라우저에서 직접 로드되는가 | **그렇다.** `<Image>` 3곳 모두 `unoptimized`다. 공식 문서: `true`면 "The source image will be served as-is from the `src`". 서빙된 HTML 5개 화면에서 `/_next/image` 참조 **0건** |
| `/_next/image`가 존재하고 무엇을 처리하는가 | **존재한다.** 로컬 경로만 처리하고 외부 URL은 전부 400 |

`images.unoptimized`(전역) 미설정 · `localPatterns` 미설정(=모든 로컬 경로 허용) ·
커스텀 `loader` 없음 · 관련 `rewrite` 없음.

### 판단

**현재 설정에서 `/_next/image`를 통한 SSRF는 성립하지 않는다.** 외부 호스트·내부 IP·
메타데이터 주소가 전부 400이다. 다만 그 이유는 이전 설명과 다르다 —
**엔드포인트가 없어서가 아니라 외부 호스트 허용목록이 비어 있어서**다.
`remotePatterns`를 나중에 여는 순간 이 표면이 생기며, 그때는 호스트 허용목록을 좁게 잡아야 한다.

**코드는 고치지 않았다.** 설명만 틀렸고 동작은 안전하다. 이미지 기능을 끄지 않았다.

### GHSA-2xp9-vwfh-vxw4 (AVIF 이미지 최적화 RCE)와의 관계

영향 버전(`>=10.0.0 <15.5.24`)에 14.2.35가 포함됐던 것은 **사실**이다.
다만 이 저장소에서 **실제 악용 조건이 충족됐다는 뜻은 아니다** — 공격자가 AVIF를
최적화기에 넣으려면 로컬 경로로 넣어야 하는데 이 앱에는 **업로드 기능이 없다.**
현재 15.5.25로 패치된 상태이므로 어느 쪽이든 닫혀 있다.

### 3-1. GHSA-955p — "해당 없음" 판정을 정정한다 (2026-09-11 2차)

직전 정리에서 "액션마다 인가를 하므로 **해당하지 않는다**"고 적었다. 공지 원문과 맞지 않는다.

공지 본문(인용):

> **Impact** — "In Next.js applications using App Router, Server Actions (`use server`) or
> `use cache` endpoints can be disclosed bypassing any authentication on the pages"
>
> **Workarounds** — "Never assume any authentication claims at the `use cache` or `use server`
> boundary. Always authenticate within the boundary."

세 가지를 나눠 적어야 맞다.

| 구분 | 사실 |
|---|---|
| **과거 버전(14.2.35)의 영향 여부** | **영향 버전에 포함됐다.** 식별자 노출은 "publicly served client artifacts"를 통해 일어나며, 앱이 인가를 어디에 두든 **노출 자체는 발생한다** |
| **액션 내부 인가가 하는 일** | 공지가 **Workaround로 제시한 바로 그것**이다. 노출을 막는 것이 아니라 **노출의 결과(권한 없는 실행)를 제한**한다. 이 저장소는 그 Workaround를 따르고 있었고, 2026-09-11 서버 액션 재생 실측으로 다시 확인했다 |
| **현재 설치 버전** | `next@15.5.25` ≥ 수정 버전 `15.5.21` → **패치됨** |

즉 "내부 인가가 있으니 이 공지는 해당 없음"은 성립하지 않는다.
**과거 버전에서 노출은 있었고, 내부 인가는 그 결과를 줄였을 뿐이며, 지금은 패치로 닫혔다.**

## 5. 폼 저장 흐름 실측 (2026-09-11 2차)

직전 회차에서 "`VetClinicForm`에 `name` 있는 input이 없어 브라우저 E2E를 중단했다"고 적었다.
**중단 사유가 되지 못한다.** 입력은 `<label>`로 감싸여 있어 접근성 이름으로 잡을 수 있었고,
`getByLabel()` / `getByRole()`로 전부 조작했다.

### 5-1. 고친 접근성 결함

`ServiceSection`의 라디오 8개(영어 응대 4 · 야간 진료 4)에 **`name`이 없었다.**
`name` 없는 라디오는 브라우저가 **한 묶음으로 보지 않는다** — 화살표 키 이동이 안 되고
보조기술은 낱개 버튼으로 읽는다. 두 묶음이 `AVAILABLE`·`CONDITIONAL`·`UNAVAILABLE`·`UNKNOWN`
**같은 라벨 네 개**를 써서 서로 구분되지도 않았다.

`group` prop을 받아 `name={group}`을 주고 감싸는 `div`에 `role="radiogroup" aria-label={title}`을
붙였다. 제출은 여전히 `payload` 하나로만 나가므로(`actions.ts:18`) **저장 구조는 그대로다.**

### 5-2. 검증 결과

| 확인 | 결과 |
|---|---|
| 병원 등록: 화면 입력 → 저장 | ✅ `/ko/admin/vets`로 이동하고 관리자 목록에 나타난다 |
| 재진입 시 값 유지 | ✅ 편집 화면에 이름·주소·전화·공식 링크가 그대로 채워진다 |
| 기존 병원 수정 | ✅ 전화·공식 링크 수정 → 저장 → **새로고침 후에도 유지** |
| 격리 DB 값 일치 | ✅ `phone=042-999-8888` · `website=https://clinic.example.com/updated` 폼과 동일 |
| 병원 폼 URL 거부 | ✅ `javascript:` · `data:` · `//evil.example.com` 모두 `invalidInput / website: Invalid input` 표시 후 등록 화면에 머문다 |
| 장소 폼 URL 거부 | ✅ `website`·`verification.sourceUrl` 각각 **`올바른 URL 형식을 입력해주세요 (예: https://example.com).`** (장소 폼은 번역된 문구가 나온다) |
| 장소 폼 정상 저장 | ✅ 두 URL 모두 정상일 때 `Place` 행 생성 확인 |
| 반려견 폼(USER) | ✅ 다이얼로그에서 이름·크기 입력 → 등록 → 목록 노출. DB에 `userId`가 로그인 사용자로 묶여 저장 |
| **DB 전수 확인** | ✅ `VetClinic.website` / `VetVerification.sourceUrl`에 `javascript:`·`data:`·`//` 로 시작하는 행 **0건** |

### 5-3. 페이지 접근과 서버 액션 인가를 나눠서 확인했다

페이지 리디렉션만으로는 서버 액션 인가를 확인한 것이 아니다. 그래서
**ADMIN이 실제로 보낸 서버 액션 POST를 그대로 캡처해 세션만 바꿔 재생**했다.

| 재생 세션 | DB에 행이 생겼나 |
|---|---|
| 세션 없음 | **아니오** |
| `USER`(비관리자) | **아니오** |
| 서명 훼손 토큰 | **아니오** |
| `ADMIN` (대조군) | **예** — 재생 방식 자체는 동작한다 |

대조군이 성공했으므로 위 3건의 실패는 **재생이 잘못된 것이 아니라 인가가 막은 것**이다.
운영 코드에 인증 우회 경로는 넣지 않았다. 테스트 세션은 격리 환경 전용 `AUTH_SECRET`으로 발급했다.

### 5-4. 관찰만 하고 고치지 않은 것

- 병원 관리자 폼의 오류 문구가 `invalidInput` / `website: Invalid input`처럼 **번역되지 않은
  개발자용 문자열**이다. 장소 폼은 번역돼 있다. 보안 문제는 아니며 `PROJECT_STATUS` §15의
  관리자 폼 i18n 과제에 해당한다.
- 반려견 폼의 견종 입력(콤보박스)에 접근성 이름이 없다. 이번 검증에 필요하지 않아 건드리지 않았다.

## 6. Vitest 공지 재검증 (2026-09-11 2차)

직전 보고의 "devDependency `vitest`에 critical 2건"은 **부정확했다.**

`npm audit --json` 확인 결과:

| 사실 | 내용 |
|---|---|
| `vitest` **패키지 집계** 등급 | critical |
| 그 아래 **실제 공지** | **GHSA-5xrq-8626-4rwp = critical**, **GHSA-82fw-gwwq-j7x9 = moderate** |
| 즉 critical 공지는 | **1건**이지 2건이 아니다 |
| GHSA-82fw는 | `@vitest/mocker`와 `vitest` **양쪽에 집계된 같은 공지**다(advisory id 1193683/1193684, 같은 GHSA) |
| `npm audit --omit=dev` | vitest 계열이 **아예 없다** — 프로덕션 트리에 포함되지 않는다 |

**공식 원문** (GHSA-5xrq-8626-4rwp / CVE-2026-47429, Critical CVSS 9.8):

> "Only users that match either of the following conditions are affected: explicitly exposes
> the Vitest UI server to the network (using `--api.host` or api.host config option)
> [or] running the Vitest UI or Browser Mode on Windows"
