# N-2 결정안 — 요약·구역 정보가 어긋나는 장소의 `실내 가능` 필터 처리

**상태: 미확정 (결정안).** 이 문서의 제안은 **코드에 반영하지 않았다.** 확정되면 그때 구현한다.

- 작성 2026-09-10 · 근거 코드 `src/lib/places/filtering.ts` · `src/lib/places/dog-access.ts`
- 관련 확정 규칙: 기획서 v3 §6-4 **D-03·D-12** · 개발명세서 v2 §5-3 · DESIGN.md §3.3

## 1. 결정이 필요한 범위는 한 가지뿐이다

`실내 가능` 필터는 지금 **요약 컬럼 하나만** 본다.

```ts
// filtering.ts
if (filters.indoor !== "all" && place.indoor !== INDOOR_FILTER_MATCH[filters.indoor]) return false;
// INDOOR_FILTER_MATCH.indoor === "allowed"
```

공통 해석(`resolveDogAccess`)이 내놓는 7개 상태를 이 규칙에 대보면 **여섯은 이미 원하는 결과**이고,
어긋나는 것은 **`conflict`(요약과 구역 기록이 서로 반대로 말하는 경우) 하나**다.

| # | 상태 | `resolveDogAccess` | 현재 `실내 가능` 필터 | 제안 | 전체 목록 문구 (변경 없음) |
|---|---|---|---|---|---|
| 1 | 실내 허용이 확인됨 | `allowed` | 통과 | **통과** | `실내 가능` |
| 2 | 실내 허용 + **크기별 구역 예외**(예: 대형견만 실내 불가) | `allowed` | 통과 | **통과 (유지)** | `실내 가능` + 구역 기록 줄 |
| 3 | 일부 구역만 허용 | `partialArea` | 제외 | **제외 (유지)** | `일부 구역 가능` |
| 4 | 야외·테라스만 가능 | `outdoorOnly` | 제외 | 제외 | `실외/테라스만 가능` |
| 5 | 반려견 동반 전체 불가 | `notAllowed` | 제외 | 제외 | `동반 불가` |
| 6 | 동반 여부 미확인 | `unknown` | 제외 | 제외 | `실내 동반 미확인` |
| 7 | 실내 불가 + 야외 미확인 | `indoorBlockedOutdoorUnconfirmed` | 제외 | 제외 | `실내 동반 불가 · 야외 동반 미확인` |
| **8** | **요약 `실내 가능` + 구역 기록 `실내·전체·불가`** | **`conflict`** | **통과** | **제외** | `동반 조건 정보 불일치` |

**2번을 3번으로 끌어내리지 않는다.** 크기별 구역 예외는 장소가 실내 허용이라는 사실을 뒤집지
않는다(`dog-access.ts`는 `appliesToSize === "ALL"`인 기록만 충돌로 본다). 마찬가지로 **3번을
1번으로 올리지 않는다** — 일부 구역 허용은 전체 실내 허용이 아니다.

## 2. 이미 확정된 규칙에 비춰 본 판단

D-03·D-12는 이렇게 정해 두었다.

> "실내 가능", "이동장 불필요"처럼 **특정 조건을 충족한 곳을 찾는 필터는 확인된 일치 값만
> 포함**한다. 미확인(`확인 필요`) 장소는 자동으로 제외된다.
> — 기획서 v3 §6-4

**요약과 세부가 서로 반대로 말하는 장소는 "확인된 일치 값"을 가진 장소가 아니다.** 서비스는
이미 이 장소를 사용자에게 `동반 조건 정보 불일치`로 표시하고 방문 판정도 `확인 필요`로 낮춘다
(`eligibility.ts`, `condition-rows.ts`). 즉 **표시·판정은 이미 "미확인"으로 다루는데 필터만
"확인됨"으로 다룬다.** 이 비대칭이 문제의 전부다.

따라서 결정할 것은 새 정책이 아니라 **좁은 해석 하나**다.

> **결정 항목 D-13(제안)** — 요약 컬럼과 `policyDetails.spaceExceptions`가 어긋나는 장소를
> 긍정 조건 필터에서 `UNKNOWN`과 같게 볼 것인가?
>
> - **안 A (권장)**: 같게 본다 → 필터에서 제외. D-03의 "확인된 일치 값만"을 공통 해석 결과에
>   적용한다. 구현은 `filterPlaces`가 `resolveDogAccess(place.indoor, place.policyDetails).key`를
>   보게 하는 것뿐이다.
> - **안 B**: 요약 컬럼을 우선한다 → 현재대로 통과. 관리자가 마지막에 고른 값이 요약이라는
>   전제가 필요하지만, 지금 요약 컬럼은 `condition-consistency.ts`가 상세에서 **자동 계산**하기도
>   하므로 그 전제가 항상 참은 아니다.

**권장은 안 A다.** 사용자가 `실내 가능`으로 거른 목록에 "실내 불가라고도 적힌 곳"이 섞이는 것은
D-03이 "서비스가 가장 크게 신뢰를 잃는 지점"이라고 지목한 상황과 같다.

## 3. 노출 문구 — 바꿀 것이 없다

제안은 **필터 통과 여부만** 바꾼다. 전체 목록(`실내 가능` 필터를 걸지 않은 상태)에서는 지금도
불일치 장소가 `동반 조건 정보 불일치`로 보이고 방문 판정은 `확인 필요`다. 즉 "필터에서는 빼되
전체 목록에서는 확인 필요로 보여 준다"는 요구는 **이미 충족돼 있다.** 새 문구·새 상태가 필요 없다.

## 4. 영향 범위

| 구분 | 영향 |
|---|---|
| **현재 공개 데이터(4곳)** | **없다.** 네 곳 모두 `policyDetails`가 NULL이라 `conflict`가 성립하지 않는다. 필터 결과가 한 건도 바뀌지 않는다 |
| 고정 사례(테스트) | 8번 사례가 `통과 → 제외`로 바뀐다. `filtering.test.ts`에 사례 추가 필요 |
| 다른 필터 | 이동장·크기·신선도 필터는 `policyDetails`와 무관하므로 그대로 |
| 성능 | `filterPlaces`가 이미 메모리에 있는 `policyDetails`를 읽을 뿐 추가 조회 없음 |
| 되돌리기 | 필터 한 줄이라 되돌리기 쉽다 |

**즉 지금 확정해도 사용자가 보는 결과는 당장 달라지지 않는다.** 구역 예외를 입력한 장소가
생기는 시점부터 효력이 생기므로, 그 데이터가 들어오기 전에 정해 두는 편이 안전하다.
