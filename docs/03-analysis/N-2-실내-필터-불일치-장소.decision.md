# D-15 — 요약·구역 정보가 어긋나는 장소의 `실내 가능` 필터 처리

## 0. 적용 범위 — `실내 가능` 필터 하나뿐

이 문서가 처음에 쓴 "긍정 조건 필터"라는 표현은 넓었다. **확정 범위는 `실내 가능` 필터다.**

- 이동장·유모차, 크기, 신선도 등 **다른 필터에 불일치 제외를 일괄 적용하지 않는다.**
- 다른 필터가 함께 선택되면 **각 필터의 기존 조건도 그대로** 적용된다.
- 실내 허용 / 일부 구역 허용 / 야외만 / 동반 불가 / 미확인의 **기존 필터 동작을 유지**한다.
- 실내 허용에 **크기별 구역 예외**가 붙는 사례도 기존 확정 정책대로 통과시킨다.
- **저장 데이터를 바꾸지 않는다.** `conflict`를 `UNKNOWN`으로 적어 넣지 않고 필터 통과 여부만 정한다.

## 1. 바뀌는 것은 한 가지뿐이다

확정 전 `실내 가능` 필터는 **요약 컬럼 하나만** 봤다.

```ts
// filtering.ts
if (filters.indoor !== "all" && place.indoor !== INDOOR_FILTER_MATCH[filters.indoor]) return false;
// INDOOR_FILTER_MATCH.indoor === "allowed"
```

공통 해석(`resolveDogAccess`)이 내놓는 7개 상태를 이 규칙에 대보면 **여섯은 이미 원하는 결과**이고,
어긋나는 것은 **`conflict`(요약과 구역 기록이 서로 반대로 말하는 경우) 하나**다.

| # | 상태 | `resolveDogAccess` | 확정 전 | 확정 후 | 전체 목록 문구 (변경 없음) |
|---|---|---|---|---|---|
| 1 | 실내 허용이 확인됨 | `allowed` | 통과 | **통과** | `실내 가능` |
| 2 | 실내 허용 + **크기별 구역 예외**(예: 대형견만 실내 불가) | `allowed` | 통과 | **통과 (유지)** | `실내 가능` + 구역 기록 줄 |
| 3 | 일부 구역만 허용 | `partialArea` | 제외 | **제외 (유지)** | `일부 구역 가능` |
| 4 | 야외·테라스만 가능 | `outdoorOnly` | 제외 | 제외 | `실외/테라스만 가능` |
| 5 | 반려견 동반 전체 불가 | `notAllowed` | 제외 | 제외 | `동반 불가` |
| 6 | 동반 여부 미확인 | `unknown` | 제외 | 제외 | `실내 동반 미확인` |
| 7 | 실내 불가 + 야외 미확인 | `indoorBlockedOutdoorUnconfirmed` | 제외 | 제외 | `실내 동반 불가 · 야외 동반 미확인` |
| **8** | **요약 `실내 가능` + 구역 기록 `실내·전체·불가`** | **`conflict`** | **통과** | **제외** | `동반 조건 정보 불일치` |

**2번을 3번으로 끌어내리지 않는다.** 크기별 구역 예외는 장소가 실내 허용이라는 사실을 뒤집지
않는다(`dog-access.ts`는 `appliesToSize === "ALL"`인 기록만 충돌로 본다). 마찬가지로 **3번을
1번으로 올리지 않는다** — 일부 구역 허용은 전체 실내 허용이 아니다.

## 2. 이미 확정된 규칙에 비춰 본 판단

D-03·D-12는 이렇게 정해 두었다.

> "실내 가능", "이동장 불필요"처럼 **특정 조건을 충족한 곳을 찾는 필터는 확인된 일치 값만
> 포함**한다. 미확인(`확인 필요`) 장소는 자동으로 제외된다.
> — 기획서 v3 §6-4

**요약과 세부가 서로 반대로 말하는 장소는 "확인된 일치 값"을 가진 장소가 아니다.** 서비스는
이미 이 장소를 사용자에게 `동반 조건 정보 불일치`로 표시하고 방문 판정도 `확인 필요`로 낮춘다
(`eligibility.ts`, `condition-rows.ts`). 즉 **표시·판정은 이미 "미확인"으로 다루는데 필터만
"확인됨"으로 다룬다.** 이 비대칭이 문제의 전부다.

따라서 결정할 것은 새 정책이 아니라 **좁은 해석 하나**다.

> **D-15 (확정)** — 요약 컬럼과 `policyDetails.spaceExceptions`가 어긋나는 장소는
> `실내 가능` 필터에서 `UNKNOWN`과 같게 본다. 즉 **제외한다.**
>
> 검토했던 대안(요약 컬럼 우선 → 현재대로 통과)은 채택하지 않았다. 요약 컬럼은
> `condition-consistency.ts`가 상세에서 **자동 계산**하기도 하므로 "관리자가 마지막에 고른
> 값"이라는 전제가 항상 참이 아니다.

사용자가 `실내 가능`으로 거른 목록에 "실내 불가라고도 적힌 곳"이 섞이는 것은 D-03이
"서비스가 가장 크게 신뢰를 잃는 지점"이라고 지목한 상황과 같다.

## 3. 노출 문구 — 바꿀 것이 없다

D-15는 **필터 통과 여부만** 바꾼다. 전체 목록(`실내 가능` 필터를 걸지 않은 상태)에서는 지금도
불일치 장소가 `동반 조건 정보 불일치`로 보이고 방문 판정은 `확인 필요`다. 즉 "필터에서는 빼되
전체 목록에서는 확인 필요로 보여 준다"는 요구는 **이미 충족돼 있다.** 새 문구·새 상태가 필요 없다.

## 4. 영향 범위

| 구분 | 영향 |
|---|---|
| **현재 공개 데이터(4곳)** | **없다.** 네 곳 모두 `policyDetails`가 NULL이라 `conflict`가 성립하지 않는다. 필터 결과가 한 건도 바뀌지 않는다 |
| 고정 사례(테스트) | 8번 사례가 `통과 → 제외`로 바뀐다. `filtering.test.ts`에 6건 추가 |
| 다른 필터 | 이동장·크기·신선도 필터는 `policyDetails`와 무관하므로 그대로 |
| 성능 | `filterPlaces`가 이미 메모리에 있는 `policyDetails`를 읽을 뿐 추가 조회 없음 |
| 되돌리기 | 필터 분기 한 곳이라 되돌리기 쉽다 |

**즉 확정해도 사용자가 보는 결과는 당장 달라지지 않는다.** 구역 예외를 입력한 장소가
생기는 시점부터 효력이 생기므로, 그 데이터가 들어오기 전에 정해 두는 것이 이번 확정의 목적이다.

## 5. 구현 위치

**`src/lib/places/filtering.ts` `filterPlaces`** 한 곳이다.

```ts
if (filters.indoor !== "all") {
  if (
    filters.indoor === "indoor" &&
    resolveDogAccess(place.indoor, place.policyDetails).key === "conflict"
  ) {
    return false;
  }
  if (place.indoor !== INDOOR_FILTER_MATCH[filters.indoor]) return false;
}
```

충돌 판정은 화면들이 쓰는 `resolveDogAccess`를 **그대로 재사용**한다. 화면별로 따로 해석하면
목록과 카드가 다른 근거로 같은 장소를 말하게 된다.

**목록·지도·개수·빈 상태가 한 경로를 공유한다.** `usePlaceListState` →
`getFilteredAndSortedPlaces` → `filterPlaces`의 결과(`filteredAndSorted` → `visiblePlaces`)를
`PlacesClient`가 목록 렌더·`list.resultCount`·빈 상태 분기·`<PlaceMap places={…}>`에 모두 쓴다.
따라서 필터 한 곳을 고치면 네 표면이 함께 맞는다.
