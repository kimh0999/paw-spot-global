# D-21 — `handling`의 이동장 의무를 `이동장·유모차 필수 아님` 판정에 반영한다

**상태: 확정 · 구현 완료 (2026-09-13).**

> 매장 내 상태(`policyDetails.handling`)가 이동장 사용을 **실제로 요구**하면, 요약 컬럼이
> `NOT_REQUIRED`여도 `필수 아님`으로 보지 않는다. 안기(`HELD_BY_OWNER`)처럼 이동장이 아닌
> 행동 의무는 이 판정을 뒤집지 않는다. **저장 데이터는 바꾸지 않고 읽는 자리에서 해석한다.**

- 작성 2026-09-13 · 해석 `src/lib/places/carrier-requirement.ts` · 필터 `src/lib/places/filtering.ts`
- 관련 확정 규칙: 기획서 v3 §6-4 **D-03·D-12** · **D-15**(`N-2-실내-필터-불일치-장소.decision.md`) · `DESIGN.md` §9
- **ID 주의**: `D-16`~`D-20`은 동물병원 도메인(`docs/02-design/동물병원-탐색-문의-P0.design.md` §2)이
  이미 쓰고 있다. `D-13`·`D-14`도 기획서 v3 §16-2가 예약해 두었다. 충돌을 피해 **D-21**을 부여한다.

## 0. 무엇이 문제였나

쓰기 시점에 요약 컬럼을 맞추는 `condition-consistency.ts`의 `collectEvidence()`는
**`details.preparation`만 순회한다**(파일 전체에 `handling` 참조 0건). 컬럼을 파생하는 항목도
`CARRIER_COLUMN_ITEMS = ["CARRIER", "CRATE", "STROLLER"]` 세 준비물뿐이다.

그래서 아래가 저장 가능하고, `이동장·유모차 필수 아님` 필터를 그대로 통과했다.

```jsonc
// PlaceCondition
"carrierStrollerPolicy": "NOT_REQUIRED",
// policyDetails.handling — 컬럼을 건드리지 않는다
[{ "mode": "UNKNOWN", "scope": "INDOOR",
   "rules": [{ "rule": "IN_CARRIER", "status": "REQUIRED" }] }]
```

즉 **상세는 `실내에서는 이동장 또는 유모차가 필요`라고 하는데 목록만 `필수 아님`으로**
통과시켰다. D-15가 실내 필터에서 없앤 것과 **같은 종류의 비대칭**이다.

## 1. 확정 내용

`preparation`은 그대로 둔다. **`handling`의 `IN_CARRIER`만** 이동장 의무로 읽는다.

| `handling` 묶음 | 이동장 의무 | 왜 |
|---|---|---|
| 행동 1개 · `IN_CARRIER: REQUIRED` | **선다** (범위대로) | 대신할 수단이 없다 |
| `ALL_OF` · `IN_CARRIER` 포함 | **선다** (범위대로) | 모두 지켜야 한다 |
| `ANY_OF` · `IN_CARRIER` 포함 | **서지 않는다** | "안고 계시거나 이동장에" — 대신할 수단이 **확인됐다** |
| `UNKNOWN` 묶음(행동 2개 이상) · `IN_CARRIER` 포함 | **미확인** | 관계를 확인하지 못했다. `필요 없음`이라고도 말하지 않는다 |
| `HELD_BY_OWNER` · `ON_LEASH_FLOOR` · `PET_SEAT` · `ON_CHAIR_OR_TABLE` · `FREE_ROAM` | **서지 않는다** | 이동장 사용 의무가 아니다 |
| `IN_CARRIER`의 status가 `ALLOWED`·`PROHIBITED` | **서지 않는다** | 사용 허용·금지는 요구가 아니다 |
| `IN_CARRIER`의 status가 `CONDITIONAL`·`UNKNOWN` | **미확인** | 조건부 의무이거나 확인되지 않았다 (아래) |
| `IN_CARRIER` 항목이 여럿이고 그중 하나가 `CONDITIONAL`·`UNKNOWN` | **미확인** | 이동장을 반드시 쓴다고 말할 근거가 없다 |
| `IN_CARRIER`는 `REQUIRED`이고 **다른 행동만** `CONDITIONAL`·`UNKNOWN` (`ALL_OF`) | **선다** (범위대로) | 다른 축의 불확실성이다. 확인된 이동장 의무를 지우지 않는다 |

묶음 모드 기준은 준비물 그룹(`collectEvidence`의 `isAlternativeGroup`)과 같다 — 행동이
하나뿐인 묶음은 `mode`와 무관하게 택일이 아니다.

**`status`를 먼저 본다 (2026-09-13 정정).** 초안은 `REQUIRED`가 아닌 네 값을 한 줄로 묶어
모두 `서지 않는다`로 적었다. 이는 **관리자 입력의 뜻과 어긋난다.**

| status | 관리자 입력 | 표시 문구 | 뜻 |
|---|---|---|---|
| `ALLOWED` | 가능 | `…도 됩니다` | 사용 허용 — 의무 아님 |
| `PROHIBITED` | 불가 | `…서는 안 됩니다` | 사용 금지 — 의무 아님 |
| `CONDITIONAL` | 상황에 따라 | `…해야 하는 경우가 있습니다` | **조건부 의무** |
| `UNKNOWN` | 미확인 | `…해야 하는지 확인되지 않았습니다` | **정보 미확인** |

`CONDITIONAL`은 **조건부 허용이 아니라 조건부 의무**다. 어떤 상황에서 걸리는지는 구조화돼
있지 않아 반영할 조건이 없으므로, `필요 없음`으로 내려 읽으면 있을 수 있는 의무를 지운다.
`UNKNOWN`도 확인하지 못한 것을 충족으로 바꿔 읽는 일이다. **둘 다 D-03을 어긴다** — 그래서
`notRequired`가 아니라 `unknown`으로 둔다. 순위가 `unknown < requiredIndoor`이므로 다른
근거로 이미 확정된 의무는 그대로 남고, 낮아지지 않는다.

**의무 여부와 다른 축의 불확실성을 구분한다.** 판정하는 것은 `IN_CARRIER`의 status 하나다.
`ALL_OF` 묶음에서 `IN_CARRIER`가 `REQUIRED`이면 같은 묶음의 안기·목줄이 `상황에 따라`든
`미확인`이든 **이동장 의무는 범위대로 선다** — `ALL_OF`는 모두 지켜야 한다는 뜻이고, 다른
행동 축의 불확실성을 이동장 의무로 옮기면 확인된 사실을 지운다. 수단도 흐려지지 않아
`means`는 `carrier`다. 반대로 `IN_CARRIER` 항목이 여럿이고 그중 하나가 `CONDITIONAL`·`UNKNOWN`이면
이동장 자체를 단언할 수 없으므로 미확인이다.

> 두 모양 모두 **관리자 입력으로는 저장되지 않는다** — `행동 2개 이상은 모두 REQUIRED여야
> 합니다`(`policy-details-form.ts`). 옛 데이터를 자동으로 고치지 않기로 했으므로 읽는
> 자리에서 방어하고 회귀 테스트로 고정한다.

`unknown`은 **`이동장·유모차 필수 아님` 필터에서만 빠진다.** 목록에서 사라지지 않으며,
카드·상세는 `이동장·유모차 필요 여부 미확인`으로 있는 대로 알려 준다. 저장된
`CONDITIONAL`·`UNKNOWN`은 그대로 남아 상세의 행동 문장(`policy-sentences.ts`)이 각자의
뜻으로 말한다 — 해석은 요약 한 줄을 정할 뿐 원본을 덮지 않는다.

**범위(`scope`) 옮기기.** `CarrierStrollerPolicy`에는 실외 전용 값이 없다.

| `scope` | 결과 |
|---|---|
| `ALWAYS` | `requiredAlways` |
| `INDOOR` | `requiredIndoor` |
| `OUTDOOR` · `UNKNOWN` | **`unknown`** — 의무가 있다는 사실만 남기고 범위는 단언하지 않는다 |

실외 전용 의무를 `실내에서 필요`로 옮기면 없는 사실을 만들고, `필수 아님`으로 두면 있는
의무를 지운다. 그래서 어느 쪽도 하지 않는다.

**끌어올리기만 한다.** 요약 컬럼이 이미 더 강하게 말하면(`REQUIRED_ALWAYS`) 세부 정책이
`INDOOR`라고 해서 낮추지 않는다. 순위는 `notRequired < unknown < requiredIndoor < requiredAlways`이며,
`unknown`이 `notRequired`보다 위인 것은 "확인되지 않음"을 "필요 없음"으로 내려 읽지 않기 위해서다(D-03).

## 2. D-15와의 관계

| | D-15 (2026-09-10) | **D-21 (이번)** |
|---|---|---|
| 대상 축 | 동반 가능 여부 (`indoor`) | 이동장·유모차 사용 의무 (`carrierStrollerPolicy`) |
| 읽는 세부 정책 | `policyDetails.spaceExceptions` | `policyDetails.handling` |
| 하는 일 | 요약과 구역 기록이 **어긋나면** 필터에서 제외 | 세부 정책이 말하는 의무로 요약을 **끌어올림** |
| 저장 데이터 | 바꾸지 않는다 | 바꾸지 않는다 (**같다**) |
| 구현 위치 | `filterPlaces` 안의 분기 | **공통 해석 함수** `resolveCarrierRequirement` |

**왜 범위를 넓혔나.** D-15 문서 §0은 "다른 필터에 불일치 제외를 일괄 적용하지 않는다"고
적었다. 그 문장은 **`spaceExceptions` 기반 불일치 판정**을 다른 축으로 번지게 하지 말라는
뜻이었고, 지금도 유효하다 — 이번 변경은 구역 기록을 이동장 판정에 쓰지 않는다.

D-21이 다루는 것은 다른 문제다. `handling`의 `IN_CARRIER`는 **이동장 의무 그 자체**이지
다른 축의 정보가 아니다. 컬럼이 그 사실을 담지 못하는 것은 파생 규칙의 공백이지 정책이 아니다.
따라서 이것은 D-15의 예외 확대가 아니라 **누락된 근거를 같은 축에서 마저 읽는 일**이다.

**왜 필터에 분기를 두지 않았나.** D-15는 `filterPlaces` 안에 분기를 뒀는데, 그 결과 필터만
`resolveDogAccess`를 호출하고 표시 계층은 각자 읽는 구조가 남았다. 이번에는 해석을
`resolveCarrierRequirement` 한 곳에 두고 **필터·카드·미리보기·상세·정렬이 모두 그것을 호출**한다.
한 곳이라도 요약 컬럼으로 되돌아가면 회귀 테스트가 깨진다.

**왜 쓰기 경로(`deriveCarrierColumn`)를 고치지 않았나.** 두 가지 이유다.
① 쓰기 시점 파생을 바꿔도 **이미 저장된 행은 고쳐지지 않는다** — 읽는 자리를 고쳐야 한다.
② D-15가 세운 "저장 데이터를 바꾸지 않고 판정만 정한다"는 원칙을 따른다.
관리자 폼의 `자동 계산됨` 잠금 규칙(`policy-details-admin-ui`)도 그대로 둔다.

## 3. 함께 바로잡은 것 — `안기` 표시

요약값 `REQUIRED_INDOOR` 하나만 보고 **안기를 대체 수단으로 단언**하던 문구가 있었다.

| 자리 | 이전 | 이후 |
|---|---|---|
| `places.card.carrierStroller.requiredIndoor` | `실내에서는 이동장, 유모차, 안기 중 하나가 필요` | `실내에서는 이동장 또는 유모차가 필요` |
| `places.preview.conditions.carrierIndoor` | 〃 | 〃 |
| `places.detail.beforeYouGo.carrier.required_indoor` | 〃 | 〃 |
| en (위 세 자리) | `Carrier, stroller, or holding required indoors` | `Carrier or stroller required indoors` |
| `admin.places.carrier.REQUIRED_INDOOR` | `실내 안기·유모차` / `Hold/stroller indoors` | `실내에서 필수` / `Required indoors` |
| `PlaceForm.tsx` `CARRIER_STROLLER_LABELS` | `실내 안기·유모차` | `실내에서 필수` |

근거: 컬럼을 파생하는 항목은 `CARRIER`·`CRATE`·`STROLLER`뿐이고 **안기는 `handling`의 다른 축**이다.
`DESIGN.md` §9가 이미 "필드명으로 대체 가능 여부를 추정하지 않는다" · "근거가 그 그룹에 없으면
컬럼 값만으로 `또는`이라고 단정하지 않는다"고 정해 두었는데, 같은 절의 정식 문구표만 안기를
담고 있었다. **문구표를 규칙에 맞췄다.** 안기는 `handling` 축의 근거가 있을 때 그 축의
문장(`policy-sentences.ts`)으로만 말한다.

`places.selectedPlacePanel.conditions.carrier.requiredIndoor`(`실내 안기·유모차`)는 참조 0건인
죽은 키라 건드리지 않았다 — `DESIGN.md` §13 F-1에 이미 등록된 별건이다.

D-15와 같은 이유다.
